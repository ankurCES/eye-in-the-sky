# REVIEW_TECHNICAL — PLAN_DRAFT.md (v0.1)

**Reviewer:** principal systems-engineering review (AirSim / GEV / MCP)
**Verdict:** architecture is sound and well-researched. Four items must be resolved in design before Phase 2: altitude datum (T1), per-vehicle command serialization (T2), render/GPU headless constraints (T7), and the geo-registration gate (T7). Everything else is fix-in-place.

---

## T1 — Altitude datum is unspecified; AirSim "GPS altitude" ≠ Cesium ellipsoid height — **critical**
AirSim's GPS `geo_point` altitude is home-geopoint + NED-z with no geoid correction: whatever altitude you type into `OriginGeopoint` is silently treated as the reference, so the "MSL" in the bridge's `altMsl` field is only MSL if the operator entered MSL — and Cesium entities default to **WGS84 ellipsoid** height, not MSL. Two degrees of freedom are conflated.
**Fix:** define one canonical datum in the bridge: publish `lat, lon, altHae` (ellipsoid). Compute `hae = alt_msl + N(φ,λ)` with the `egm96-universal` undulation GEV already ships, evaluated at each sample (undulation varies across an AO). Constrain `OriginGeopoint.altitude` to be entered as **MSL** and validate once in Phase 0 (drop the drone at NED 0 and assert bridge output ≈ expected HAE). GEV side: set entity `heightReference` explicitly instead of relying on Cesium defaults. Document that `moveToGPSAsync` and `BarometerData` inherit the same home-referenced model — one conversion point in the bridge, not per-call-site conversions.

## T2 — AirSim allows ONE in-flight command per vehicle; plan has no serialization model — **critical**
`MultirotorApiBase`'s SingleCall guard means a second `*Async` while one is running either errors or is dropped, depending on version. The tool catalog's `task_handle` model doesn't say who enforces ordering, and there is no API to poll a future's progress — msgpack-rpc futures resolve only at completion.
**Fix:** MCP server owns a per-vehicle FIFO command queue + state machine (`idle → executing → cancelling → aborting`). Map each queued RPC future to a `task_handle`; store `{handle → vehicle, request_id, started_at, future}`. Progress comes from the MCP side (distance-to-target vs planned path from the 10 Hz telemetry), never from AirSim. `uav_abort` = `cancelLastTask` + `hoverAsync`, then reconcile queue state. Add a watchdog: if a future doesn't resolve within its timeout (e.g. sim paused via `simContinueForTime`), fail the handle and put the vehicle through a hover-recovery. Reject, don't queue-behind-fail: a `takeoff` arriving mid-cruise should return `busy` with the current handle, letting the harness decide.

## T3 — Camera readback cost unbounded; separate loops and lazy-subscribe — **major**
`simGetImages(compress=true)` runs a full PNG encode on the render thread per frame; multi-camera at 10 Hz will starve physics and saturate the RPC. The plan's "2–5 Hz camera" note isn't wired into an owner.
**Fix:** three independent loops in the bridge: (a) telemetry ≤10 Hz — one batched call (`getMultirotorState` + sensors), single message on the wire; (b) camera 2–5 Hz **per camera**, gated by a GEV subscriber counter — start when the first client opens the PIP, stop when the last closes; (c) on-demand only: `uav_capture_image`, `uav_get_detections`, LOS. Keep exactly one latest frame per camera (drop-on-backlog, never queue); convert PNG→JPEG in the bridge at the requested quality. Batch multiple `ImageRequest`s (Scene+Depth+IR) into one `simGetImages` call to get frame-aligned sets — the plan already relies on this; make it explicit as a rate budget.

## T4 — MCP protocol gaps: progress, idempotency, persistence, exclusion, auth — **major**
(a) Long missions (>30 s) need `notifications/progress` with `progressToken` per the MCP spec, or the harness flies blind and will re-poll. (b) A dropped Streamable-HTTP connection mid-`takeoff` followed by harness retry double-fires the command — add an idempotency key param, dedupe table keyed on it. (c) Mission state lives only in server RAM; an MCP restart mid-flight loses the mission and the fuel clock — persist an append-only JSONL mission log (commands, task transitions, fuel integrals) and on restart replay to decide resume-or-`abort_and_RTH`. (d) MCP layer must enforce the same per-vehicle mutex as T2 — tool calls are concurrent by protocol. (e) Streamable HTTP with a remote harness is a network-exposed control plane: require Bearer token auth, validate `Origin`, bind loopback by default, and do not expose msgpack-rpc :41451 outside the sim host — the bridge is the only external surface.
**Fix:** all five are v1 acceptance criteria, not backlog.

## T5 — Fuel model must be a reconciled integrator, not a countdown — **major**
Open-loop "burn rate by phase" drifts against actual flight; the plan estimates fuel at planning time but doesn't reconcile in flight.
**Fix:** server-side integrator: each telemetry tick, apply the phase burn rate to the elapsed dt, then reconcile against the synthetic clock (burn-during-integrating-DRIFT: `fuel += rate(actual_phase(v_z, speed))·dt`; recompute phase from measured climb/cruise each tick rather than the commanded one). Persist fuel state (ties to T4c). Low-fuel auto-RTH is a **safety transition, not a task**: it must pre-empt and clear any queued command (T2) and be un-cancellable by harness retries; only a dedicated operator-level override cancels it. `mission_grid_search` estimates must use the same integrator on a dry-run of the waypoint plan, not a table lookup.

## T6 — GEV: v1 should be REST-poll only; overlays need their own datasource — **major**
`getSnapshot(query,{signal})` is a poll contract; no GEV layer speaks WebSocket today, and WS adds reconnection/backoff logic in a layer that already has polling + stale handling for free.
**Fix:** v1 = `uavSim.js` is a pure REST poller of `/snapshot` at the bridge's poll cadence (respect `stale`/`freshness` from the contract); WS is a v2 upgrade behind the same source interface. Second: don't stream mission overlays through the entity snapshot — routes/geofence/grid are low-rate, mostly-static geometry; render them in a separate `Cesium.CustomDataSource` fed from `/mission-overlay` (GeoJSON), refreshed only on mission-state change. Third: cap entity property writes — push telemetry into Cesium at 2–5 Hz per entity (interpolate client-side if smoothness matters); 10 Hz per-entity writes across a multi-ship flight is where the globe starts janking. Register `'uav'` in `SOURCE_METHODS` (constructCatalog) as planned.

## T7 — Headless ≠ renderless, and geo-registration is the Phase-0 gate — **critical**
(a) `simGetImages` requires the UE render pipeline: `-nullrhi` gives black frames. The sim host needs a GPU plus either a visible window, `-RenderOffscreen`, or Xvfb on Linux. (b) Cesium-for-Unreal tiles come with their **own** georeference (CesiumGeoreference origin). If that origin doesn't coincide with AirSim's `OriginGeopoint`, every `geo_point` the bridge publishes (GPS, detections, spawned objects) is offset from the terrain GEV renders — the whole product premise breaks silently.
**Fix:** make Phase 0 an acceptance gate, not exploration: (1) place a marker mesh at a known WGS84 coordinate via lat/lon→NED→`simSetObjectPose`; (2) read it back via `simGetDetections` and `getGpsData`; (3) render drone + marker in GEV against the Cesium tileset; (4) pass tolerance (≤5 m horizontal, ≤10 m vertical, EGM96 included per T1) before any other phase starts. Verify `simTestLineOfSightToPoint` behaves in this config too. If Cesium-for-Unreal registration can't hit tolerance, the documented fallback (Blocks env, GPS math intact) applies — but then say so explicitly in the plan, because detection-overlay-over-terrain demos in GEV degrade.

## T8 — Test strategy must be defined per phase now, with a UE-free CI path — **major**
Nothing in the plan says how any of this is tested, and UE+GPU can't run in CI.
**Fix:** per phase: **P0** geo gate (T7) as a scriptable checklist + record of the chosen `OriginGeopoint`/datum. **P1 bridge:** pure unit tests of NED↔WGS84+EGM96 against golden vectors cross-checked with AirSim's own Python client on the same inputs; a fake AirSim (msgpack-rpc mock of the ~15 used RPCs, no UE needed) drives the bridge in CI. **P2 MCP:** contract tests per tool — happy path, timeout, cancel-mid-flight, queue-busy rejection, idempotency retry (T4b) — all against the fake; one GPU-host e2e as a nightly. **P3 GEV:** record/replay `/snapshot` fixtures through `uavSim.js` + layer render smoke. **P4–6:** scripted mission scenarios asserting state-machine transitions and invariants: fuel never below reserve, geofence never crossed, no command accepted while vehicle not `idle`. Determinism: seed + `simPause`/`simContinueForTime` for repeatable runs. Replay log (T4c) doubles as the debrief/replay feature the plan wants.

## T9 — Deployment topology: GPU sim host, pinned images, loopback boundaries — **minor**
Three hosts: (1) **sim host** — bare metal or VM with GPU passthrough; UE+AirSim build pinned to a fork commit + UE version; `settings.json` mounted, not baked. Linux → `nvidia-container-toolkit` + `-RenderOffscreen`/Xvfb; Windows → bare process, no Docker (UE rendering in containers is not supported there). (2) **MCP+bridge** — one container (they share the fuel/mission state), healthcheck = "can reach :41451 and `/snapshot` returns fresh". (3) **GEV** — static/CDN; browser needs CORS + the auth token from T4e to reach the bridge. Restart policy: sim host crash = detect via bridge healthcheck, expose `sim_state` in `/snapshot` so GEV shows it instead of silently going stale.
**Fix:** write the docker-compose + driver/UE/AirSim version matrix as a Phase 0 deliverable, and pin the archived AirSim fork by commit hash in a lockfile.

---

**Cross-cutting:** T1+T2+T7 are the three that, if discovered late, invalidate downstream work — they belong in the Phase 0/1 exit criteria, each with a named test. T4e (auth) is the only item I'd block any network-exposed deployment on.
